# Mid-360：SEU library 实测

更新：闭环修复与最终优化轨迹结果见 [修复报告](mid360-fix-report.md)。在线历史消息与优化关键帧需分开评价。

本测试保持 Adaptive-LIO 松耦合前端，经同帧末点云/里程计接口接入 T-DT legacy 后端，不启动 ZLIO。ScanContext/后端使用导航 Z 裁剪前的主雷达点云。

## 数据与复现

来源：https://github.com/hzc333/Livox-Mid360-SLAM-Dataset-SEU ，核查提交 `34556c419473887bada1317ac357d82ef3b4ae22`。发布者明确标注 Mid-360，声称三条轨迹闭合。Google Drive 的 `library.bag` 文件 ID 为 `1oJyPuq1aUv7BJnNSO4e-BDYsudklJDMH`。

下载文件 1,666,816,303 bytes，时长 429.830 秒；4,298 条 `livox_ros_driver2/CustomMsg` 和 85,965 条 IMU，没有真值话题。哈希与原始检查见 `seu-library-inspection.json`；哈希是本地计算值，不是发布者提供的校验值。

原包在 `/workspace/datasets/seu-library.bag`，转换结果在 `/workspace/datasets/seu-library-ros2-fast`。未改消息时间、点内 offset_time 或录制时序；与此前 Avia sensor-clock 实验不同，本次保留原始录制时序。首次慢速转换被中止，其目录 `seu-library-ros2` 不可用于回放。

```bash
/workspace/adaptive-lio-env/data-venv/bin/python tools/inspect_seu_mid360.py \
  /workspace/datasets/seu-library.bag --output-prefix /workspace/datasets/seu-library
/workspace/adaptive-lio-env/data-venv/bin/python tools/convert_avia_bag.py \
  /workspace/datasets/seu-library.bag /workspace/datasets/seu-library-ros2-fast --fast
```

目标目录必须不存在。快速转换使用 ROS2 schema 的 `ros1_to_cdr`；每话题前20条与原来的逐字段转换比较完整 CDR 字节，样本全部一致。总消息数与源包一致。

运行使用保留的 `adaptive-lio:tdt` 镜像，挂载 `/workspace`，source ROS Jazzy、`adaptive-lio-env/install`、`adaptive-lio-env/backend-install`。调用 `tools/replay_tdt.py --bag /workspace/datasets/seu-library-ros2-fast --config /workspace/datasets/seu-library.yaml --output <新目录>`；短测试增加 `--duration 60`，裁剪对照增加 `--crop`。rate=1，播放前 delay=2秒。

配置使用 `mid360-raw-reference.yaml`：Livox消息路径 lidar_type=1，blind=0.5m，gnorm=9.805，LiDAR→IMU平移 [-0.011,-0.02329,0.04412]、单位旋转。数据发布者未提供驱动坐标补偿设置，原始 LiDAR 坐标是假设，不能据此证明外参正确。没有覆盖用户实车配置。

## 初始化与数据限制

原始 IMU 时间无倒退或重复，最大间隔约7.715ms。前2秒加速度模长中位数0.99267，符合 g 单位。前1秒平均角速度约 [0.00625,-0.11744,-0.07389] rad/s，前2秒最大角速度0.72459rad/s，起始并非可确认的静止段。

前端约1秒报告初始化成功，并给出 bg=[0.00540,-0.11780,-0.07580] rad/s。`StaticIMUInit::TryInit` 主要以方差判断，没有独立的平均角速度约束；这里存在把初始转动计入零偏的风险。没有放宽初始化阈值，也没有裁掉起始运动伪造成功。后续输出正常不等于初始化正确。

运行出现 PCL “Leaf size is too small ... Integer indices would overflow” 警告；代码对应导航发布点云的0.01m VoxelGrid，完整高度的后端回调在它之前。这提示该导航降采样设置在此室外场景需要单独处理，不能将本次运行描述为无警告。

## 指标解释

结果见 `mid360-results.json`。`accepted/rejected` 是 `lio_quality` 日志行计数，本配置 diagnostic_stride=10，不代表所有帧的接受/拒绝数。状态 NORMAL 是后端自报状态；accepted_loop_log_count 是几何验证接受日志，均非真值正确率。

裁剪统计为同一个已配对的帧，在世界系施加 Z∈[-1,2]m，再变换至局部坐标计算20×60、80m最大高度描述子。它隔离了裁剪对同帧输入的影响，但不是 T-DT 默认30×90、0.6m采样、姿态整平、增广后的完整描述子实现，不能称为实际检索召回率。

轨迹首尾距离是输出坐标的端点距离；无真值、未知端点朝向/停稳和外参，不能称为ATE/RPE。短测试没有覆盖整条闭环；不同回放有线程调度和随机采样差异，跨运行轨迹变化不能单独归因于裁剪。时间间隔指标来自消息stamp，不是端到端墙钟延迟。

## 完整序列结果：接入可运行，稳定性不通过

429.8秒完整回放收到85,965条IMU（与源包总数一致），观察到85,228条前端里程计、85,224条后端位姿、4,225帧后端输入点云。4,224条状态均为NORMAL，日志有11次回环几何验证接受，无停链、非有限/非单调输出或节点崩溃，全部正常退出。backend stamp间隔p99为6.029ms、最大74.168ms；这是消息时间间隔，不是实际处理延迟。

然而，前端/后端输出首尾距离分别为31.967m/32.083m，与发布者声明的闭合路径明显不一致。本次不能通过轨迹稳定性验收，也不能把11次回环接受理解为回环正确。后端末点约[-0.280,-12.023,-29.755]m，前端Z范围[-45.537,0.376]m。没有真值及对初始世界系重力对齐的独立核验，不能直接把该Z跨度叫作实际高度误差；它仍足以说明世界固定高度窗在这次运行中不适用。

4,224个同帧配对的裁剪统计：删除97.462%点，20×60描述子非空格子均值399.237→37.754；55.232%配对帧会被Z窗完全裁空，100%描述子发生变化。这些数值仅针对本次轨迹/世界坐标，不是Mid360硬件固有损失率。完整后端输入保留了这些高度信息，导航点云仍执行原裁剪。

首60秒独立回放也无停链，但其裁剪损失为88.387%，说明全程统计明显受后续世界Z轨迹影响。优先排查初始运动被计入零偏、初始世界系与重力的关系、数据发布者驱动外参；随后检查每条回环约束与轨迹一致性。需要有真实静止起步、已确认外参和真值/独立参考的Mid360数据才能完成精度验收。当前证据支持接口与完整点云通路可用，不支持鲁棒性已解决。

## 裁剪输入对照与坐标语义

另一次原始起点60秒 `--crop` 对照完成：11,727条后端位姿，589帧点云，590条NORMAL状态，3次回环接受日志，无停链或进程异常。未裁剪60秒为2次回环接受；这个差异不能证明裁剪提高或降低正确率，必须核查候选真值。全程裁空风险也不能由该短测试消除。

代码核查：`lidarodom_m::imu_init` 将 `GetGravity()` 传给 `ESKF::SetInitialConditions`，后者设置 `g_`，并不据此旋转初始 `R_`。本包前1秒平均加速度约[-0.23352,0.04802,0.97690]g，与+Z夹角约13.714°；同时有运动，不能把该角度当作可靠静态姿态标定。因此前端 odom 的Z轴不保证是重力竖直方向，Z跨度不能直接读作物理高度变化。

T-DT 配置默认 `level_with_odom_roll_pitch: true`，其整平语义也需要与这个重力坐标约定对齐。这是本次新增的未解决适配项。应先确定重力对齐的里程计/点云共同坐标变换（含pose covariance及TF的一致变换），或明确采用不整平描述子的对照，再重做验证；不能只旋转点云或只改一个frame_id。未为了使本包通过而擅自改变前端世界坐标约定。

## 进一步诊断：32.1m及回环记录的含义

再次核查原始日志：前端首尾差31.9669m，后端32.0830m；误差在前端轨迹中已经存在，后端没有形成整圈闭合校正。这里比较的是在线发布位姿的首尾，不是最终统一优化后的全体关键帧轨迹，也不是真值ATE。

11次接受的关键帧对分别为61→46、66→50、627→612、632→617、637→621、642→627、647→623、652→637、657→641、662→647、667→648，全部只相隔15～24帧。日志delta_t仅0.0022～0.0186m。不能把这些局部约束称为成功找回整圈起点。

实际继承配置 `loop.candidate_max_distance=7.0`；`captureLoop()`先按优化位姿的欧氏距离筛候选，再做描述子检索。在输出起终点相距32m时，起点附近关键帧可能先被空间门限排除。尚未记录每个关键帧候选集，不能声称已证明某一具体起终点候选被丢弃。即使解除该门限，`verifyLoop`仍使用预测相对平移作为配准初值，只由描述子替换yaw；32m漂移可能超出局部配准收敛范围。修复应包含全局召回/多初值粗配准，并保留独立重叠、几何、PCM及NIS检查，不能仅放大接受门限。

前端初始化误把运动均值作为bg是有代码和数据支持的风险，但尚无消融实验定量证明它解释了全部32m。静止检测应拒绝该起步窗口；若要求运动中启动，需动态初始化或可信的预标定与可观测性检查。拒绝初始化属于安全改进，并不等价于这条无已确认静止段的bag已能完成定位。

固定旋转到重力对齐坐标系只能改变XYZ分量，不改变首尾欧氏距离，不能独自把32m修好。该修复解决高度裁剪/描述子整平语义。此次未裁剪完整点云已经送入后端，因此导航Z裁剪也不能直接作为该次32m首尾差的原因。

## 原始数据首尾闭合的后续核查

已补做不依赖LIO初值的原始首末帧全局配准、反向配准及点级留出验证，均估计首尾平移约0.16～0.17m，场景结构重叠。证据支持该包首尾确实回到同一地点附近，不能用“数据本来相距32m”解释在线轨迹结果。该距离是点云配准估计而非真值；细节、失败的邻近配对及图示见 `seu-endpoint-check.md`。
